Scheduler & Workflows

Drive OpenSpec changes to completion with a DAG of dependent prompts. The TUI stays your workshop for exploring ideas; the scheduler is the conductor that implements them while you keep working.

New in this release

The scheduler is a separate long-lived binary (clhorde-scheduler) that runs alongside clhorded. It is a thin client of the daemon — everything it does goes through the same IPC the TUI and CLI use. The daemon itself stays workflow-agnostic.

Two modes of working

Exploration (you ↔ Claude)

Long-lived interactive PTY. You iterate with Claude on a proposal until openspec/changes/<name>/ is in shape.

Lives in the existing Prompts tab.

Execution (scheduler ↔ Claude × N)

A DAG of dependent prompts dispatched to clhorded. Each section of tasks.md becomes a prompt; sections share a worktree, run in dependency order, and tick off their checkboxes.

Lives in the new Drafts and Workflows tabs.

You explore N ideas in parallel in the TUI. When an idea matures, you queue it — the scheduler picks it up and implements it while you keep exploring the next one. Both modes share the same worker pool bounded by max_workers.

Install & run the scheduler

The scheduler is built as part of cargo build --release. It is a separate process from clhorded:

# 1. Daemon must be running
$ clhorded &

# 2. Run the scheduler watcher in the repo you want to drive
$ cd /path/to/repo
$ clhorde-scheduler daemon

# Or watch a different root explicitly:
$ clhorde-scheduler daemon --root /path/to/repo

The scheduler:

  • Connects to clhorded over its Unix socket.
  • Watches <root>/openspec/changes/ for .clhorde-ready markers.
  • Opens its own control socket at ~/.local/share/clhorde/scheduler.sock for the TUI, web bridge, and clhorde-cli flow commands.
  • Persists workflow state to ~/.local/share/clhorde/workflows/<name>.json.
Two daemons, one CLI

You can run clhorde-cli flow daemon as a shorthand for clhorde-scheduler daemon. The flow sub-command is a verbatim wrapper that forwards every argument to the scheduler binary.

The .clhorde-ready marker

A change in openspec/changes/<name>/ is picked up by the scheduler if and only if a .clhorde-ready file sits next to its tasks.md. This is the explicit hand-off contract between exploration and execution — the scheduler never auto-promotes a draft.

The file is plain TOML. All fields are optional and unknown fields are silently ignored:

# openspec/changes/<name>/.clhorde-ready
priority = 5                       # higher runs first when workers free up
depends_on = ["add-base-auth"]      # other change names that must reach Archived first
worktree_branch = "feature/oauth"   # default: detached HEAD
parallel_sections = ["3"]           # section ids safe to run in parallel
max_section_retries = 2            # override default retry budget for this workflow

How the marker gets there

  • TUI: press Q on a draft in the Drafts tab.
  • CLI: clhorde-cli flow queue <name> [--priority N]
  • By hand: touch openspec/changes/<name>/.clhorde-ready
  • Claude itself: at the end of /opsx:propose, the agent can write the marker if you confirmed.

The scheduler removes the marker after archiving (the change leaves the queue naturally) or via clhorde-cli flow unqueue <name>. The marker is normal Git, so check it in or .gitignore it — both patterns are fine.

Workflow lifecycle

A change moves through this state machine. Most transitions are automatic; the user controls only the queue boundary.

[Drafted]     — user reviews / refines —> [Drafted]     (loops while exploring)
[Drafted]     — queue (marker file) —————> [Queued]
[Queued]      — scheduler picks up —————> [Implementing]  (apply phase, DAG dispatch)
[Implementing] — all sections done ——————> [Verifying]
[Verifying]   — ok ———————————> [Archiving]
[Archiving]   — done ——————————> [Archived]
[*]           — user cancels ———————> [Cancelled]
[*]           — failure ——————————> [Failed]     (retry possible)

State labels render in the Drafts/Workflows tabs (TUI & web) with consistent colors:

  • drafted, queued — gray / amber
  • implementing, verifying, archiving — cyan / blue
  • archived — green
  • cancelled — magenta
  • failed — red

A queued workflow whose dependencies haven't all archived shows an additional yellow · blocked annotation — see Inter-workflow dependencies.

tasks.md syntax

The scheduler parses openspec/changes/<name>/tasks.md after every worker run to figure out what's done and what runs next. The recognized syntax is a small, OpenSpec-friendly subset of Markdown:

# Plan title (free-form prose, ignored)

## 1. Theme Infrastructure
- [ ] 1.1 Create ThemeContext
- [ ] 1.2 Add CSS variables

## 2. UI Components
- [ ] 2.1 Build toggle component
- [x] 2.2 Wire it into the navbar    # already done

### 2.3 Sub-section example
- [ ] 2.3.1 Nested task

What the parser recognizes

  • ## N. Title — numbered top-level section.
  • ### N.M Title — sub-section with dotted id.
  • - [ ], - [x], - [X] — tasks. * and + work too as list markers.
  • Free-form prose between items is fine and ignored.
  • Fenced code blocks (``` or ~~~) are skipped, so task-like lines inside code samples never accidentally enter the DAG.
  • Inline <!-- ... --> comments are stripped from titles & task text but preserved on the source line for the annotations pass.
  • Tasks before the first heading and headings without a leading dotted id are dropped.

The default granularity is one prompt per leaf section. Sections run sequentially in source order: section N depends on section N−1. Override this with annotations.

DAG annotations

HTML comments on a heading or task line let you customize the DAG without leaving Markdown. The general form is:

<!-- clhorde: key value; key2 value2 -->

Multiple directives are separated by ;. Multi-value lists can be separated by , or whitespace. Unknown keys are silently ignored.

## 3. Tests <!-- clhorde: depends 2; parallel-with 4 -->
- [ ] 3.1 Unit tests
- [ ] 3.2 E2E suite <!-- clhorde: needs 2.1 -->

## 4. Docs <!-- clhorde: prompt-template apply-section-quiet -->
- [ ] 4.1 Update README

Recognized keys

KeyWhereEffect
dependssection headingSection ids this section runs after. Replaces the default sequential edge.
parallel-withsection headingSection ids that may run concurrently with this one. Recorded as a hint without removing existing edges.
needstask lineDotted task ids the annotated task depends on (used when granularity is task).
granularityany heading (first wins)section (default), task, or phase. See below.
prompt-templatesection headingOverride the template name for this section.

Granularity

  • section (default) — one prompt per leaf section. Best balance of context vs. parallelism.
  • task — one prompt per - [ ] task. Use sparingly — context overhead is steep.
  • phase — collapses everything into one big apply prompt. Falls back to OpenSpec's native flow.

Inter-workflow dependencies

depends_on = ["other-change-name", ...] in a .clhorde-ready marker holds a workflow in queued until every named dependency reaches Archived. There is no separate blocked status — a held workflow is just queued with a non-empty blocked_by list.

What blocks

Dependency stateOutcome
Drafted / Queued / Implementing / Verifying / ArchivingStays Queued, surfaced in blocked_by.
Archived (all deps)Transitions to Implementing.
CancelledDependent fails with "dependency '<name>' was cancelled".
FailedDependent fails with "dependency '<name>' failed: <reason>".
Missing change directoryDependent fails with "dependency '<name>' not found".
Cycle reachableEvery workflow in the cycle fails with "dependency cycle: A → B → A".

When a workflow archives, the orchestrator sweeps every dependent and re-evaluates — a previously-stuck workflow picks up automatically without an FS event.

Where you see it

  • CLI: clhorde-cli flow status <name> annotates each dep with its current state and adds a blocked_by: line: 
    $ clhorde-cli flow status add-oauth-login
status: queued
priority: 5
depends_on: add-base-auth (archived), shared-tokens (queued), ghost-change (not found)
blocked_by: shared-tokens, ghost-change
  • TUI: Workflows pane row gets a yellow · blocked suffix; the detail overlay header gains a Blocked by: A, B line.
  • Web: same suffix on the row (with a tooltip listing the deps); the expanded card header has a full-width Blocked by: ... line.

The blocked_by field is wire-back-compat: older clients that don't know about it simply don't render the suffix.

Prompt templates

Each phase of a workflow renders a prompt from a Tera template. Four template names are reserved:

NameUsed by
proposeclhorde-scheduler propose <idea>
apply-sectionEach section in the apply phase
verifySingle verify-phase prompt
archiveSingle archive-phase prompt (/opsx:archive)

Override layering

Resolution order, first match wins:

  1. Per-project: <root>/openspec/.clhorde-scheduler/templates/<name>.md
  2. User: ~/.config/clhorde/scheduler/templates/<name>.md
  3. Built-in: compiled into the binary, exists for every name above.

Malformed or unreadable overrides log a warning and fall through to the next layer. Only the four known names are renderable, so a stray file with a typo can't accidentally route a prompt.

$ clhorde-scheduler templates path
/home/user/.config/clhorde/scheduler/templates

$ clhorde-scheduler templates edit   # opens dir in $EDITOR

CLI: clhorde-cli flow

clhorde-cli flow <subcommand> is a thin wrapper that forwards to the clhorde-scheduler binary. You get one CLI entrypoint; the scheduler binary stays usable independently for scripting.

SubcommandEffect
flow daemon [--root PATH]Run the long-lived watcher.
flow propose <idea...>Spawn one PTY prompt running /opsx:propose <idea> and wait for a new openspec/changes/<X>/ directory.
flow queue <name> [--priority N]Write the .clhorde-ready marker. Refuses if the change directory is missing.
flow unqueue <name>Remove the marker. Idempotent.
flow draftsList unqueued OpenSpec changes.
flow status [name]List every workflow, or dump a single one with priority, deps, timestamps, prompt UUIDs, and blocked_by.
flow apply <name>One-shot dispatch of the next ready section — works even without a long-lived watcher.
flow archive <name>Run /opsx:archive for a verified change.
flow cancel <name>Remove the marker and update persisted state. A running watcher cancels through the orchestrator.
flow retry <name> --section NRe-dispatch a failed section (accepts dotted ids like 3.2).
flow templates path|editShow or open the user template directory in $EDITOR.

Add --log debug (a global flag) for verbose logs.

Standalone or watched

FS-only commands (queue, unqueue, drafts, status, templates) work without a running scheduler — they touch openspec/changes/ and ~/.local/share/clhorde/workflows/ directly. Daemon-coupled commands (apply, archive, cancel, retry, propose) need clhorded running.

TUI: Drafts & Workflows tabs

The TUI gained a top-of-screen tab bar:

 [1] Prompts   [2] Drafts   [3] Workflows

Press 1, 2, 3 from Normal mode to switch. The Prompts tab is unchanged.

Detail overlay

Press Enter on a workflow to zoom in. The overlay shows each apply-DAG node (id, label, state, prompt id, exit code, deps) plus the verify and archive singletons.

KeyAction
j / kScroll
gg / GTop / bottom
rForce-refresh detail (push events keep it live on their own)

Push, not poll

The TUI subscribes to SchedulerEvent over the scheduler control socket. Both the workflow lists and the detail overlay update reactively as the orchestrator emits diffs — no 2-second polling. Title bars carry a freshness suffix (fresh, 12s, 3m, 1h) so you can see at a glance how stale the view is. If the scheduler isn't reachable, the panes show a "scheduler not reachable — start with: clhorde-scheduler daemon" banner.

Web dashboard tabs

The web SPA gets two new top-nav tabs that mirror the TUI:

  • Drafts — list of unqueued changes. Each row has a [Queue] button.
  • Workflows — status-coloured rows. [Open] zooms into a detail block fetched on demand. [Cancel] runs a confirmed cancel. The detail block has an inline [Retry section] control. Blocked workflows show the same · blocked suffix and a Blocked by: ... line in the detail.

The browser stays live via WebSocket: the existing /api/ws endpoint now multiplexes SchedulerEvent frames alongside the daemon broadcasts. New REST routes back the SPA actions:

MethodPathPurpose
GET/api/scheduler/statusList every known workflow + the watched root + a connected flag.
GET/api/scheduler/workflow/{name}Per-workflow detail (DAG nodes + per-phase dispatch state).
POST/api/scheduler/workflow/{name}/queueBody: { "priority"?: int }. Writes the marker.
POST/api/scheduler/workflow/{name}/cancelRemoves the marker and transitions.
POST/api/scheduler/workflow/{name}/retryBody: { "section": "3.2" }. Re-dispatches one apply node.

Error mapping: 503 when the scheduler isn't running, 504 on timeout, 502 on bridge IO error, 404 for unknown workflow on detail, 400 for malformed mutations.

WebSocket envelope:

{
  "type": "SchedulerEvent",
  "event": {
    "type": "WorkflowUpdated",
    "summary": { "name": "add-oauth-login", "status": "implementing", ... }
  }
}

Variants: Snapshot, WorkflowUpdated, DetailSnapshot, DetailUpdated. The bridge starts even when the scheduler is offline — the daemon-only views (Prompts/Store) keep working — and reconnects in the background.

Auth

The --auth-token middleware on clhorde-web gates the new routes too. The scheduler control socket itself has no built-in auth and relies on filesystem permissions, exactly like the daemon socket.

Daemon primitives

Three new primitives in clhorded make the scheduler possible — and are useful on their own. They are workflow-agnostic; the daemon knows nothing about OpenSpec.

Prompt dependencies

A prompt can name other prompts as deps. It enters the new Blocked state until every dep reaches Completed. If a dep Failed, the dependent stays Blocked indefinitely (no auto-cascade; you decide what to do).

  • CLI: clhorde-cli submit "..." --depends-on 1,2,3 (alias --after).
  • Web: POST /api/prompts body field "depends_on": [1, 2].
  • Cycles are rejected with a clear error.
  • Deletion purges the dead UUID from any other prompt's depends_on.

Shared worktrees

Two prompts can share a single git worktree by carrying the same worktree_id. The daemon creates the worktree once on the first dispatch, broadcasts the resolved path to every sibling, and refcount-cleans it when the last sibling reaches a terminal state.

  • CLI: clhorde-cli submit "..." --worktree --worktree-id flow-42
  • Web: POST /api/prompts body field "worktree_id": "flow-42".
  • Retried prompts rejoin their original worktree.
  • Worktree directory layout: <repo>-wt-<sanitized-id>/ — sanitization keeps [A-Za-z0-9._-] only.

Generic prompt annotations

Each prompt now carries an opaque annotations: { string → JSON } bag the daemon stores, persists, and broadcasts but never interprets. Anyone can write keys via SetAnnotation { prompt_id, key, value }; value: null removes the key.

The well-known key openspec.affected_changes is written by the scheduler on every WorkerFinished — it lists OpenSpec changes whose files the worker touched. The TUI's Drafts tab uses this to suggest "queue this change?". Other workflow sources (Linear, GitHub Issues) can claim their own keys without touching the daemon.

End-to-end recipe

# 0. Have the daemon and the scheduler running
$ clhorded &
$ clhorde-scheduler daemon --root ~/code/myrepo &

# 1. Explore in the TUI — drafts a change.
$ clhorde
#   (in TUI) press i, type: /opsx:propose Add OAuth login
#   Claude creates ~/code/myrepo/openspec/changes/add-oauth-login/

# 2. Queue it (TUI: press 2 then Q on the row, or:)
$ clhorde-cli flow queue add-oauth-login --priority 5

# 3. Watch progress.
$ clhorde-cli flow status add-oauth-login
status: implementing
priority: 5
section_progress: 2/5
prompts: 47, 48 (active)

# 4. Keep exploring something else in parallel.
#   (in TUI) press 1, then i, new prompt: /opsx:propose Add billing dashboard

# 5. Eventually:
$ clhorde-cli flow status add-oauth-login
status: archived
duration: 18m
sections: 5
retries: 3

If a section fails:

$ clhorde-cli flow retry add-oauth-login --section 3.2

If you want to chain workflows, point one's marker at another:

# openspec/changes/add-oauth-ui/.clhorde-ready
depends_on = ["add-oauth-login"]

The add-oauth-ui workflow stays queued with blocked_by: ["add-oauth-login"] until add-oauth-login archives, then transitions automatically.
